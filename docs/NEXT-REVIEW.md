# 后续研发审查

这份文档是给下一轮研发用的设计底稿，不把“建议”写成已经完成的功能。审查基线是当前工作树的 `1.0.7`；`npm test` 当前为 612/612，通过只代表本地契约和回归用例成立。

## 先说结论

插件现在的主要风险不在工具数量，而在“这条数据属于哪个会话、哪个赛事、哪个用户”这条身份链还没有成为一个明确的对象。只要同时开两个 DSH 会话，或者在切换赛事时碰上网络抖动，团队消息、用量和面板数据就有串线的可能。

第二个问题是平台适配层和客户端仍然偏大。当前代码可以工作，但多个职责挤在少数几个文件里，后续每加一个赛段或一种 DSH 版本，回归范围都会扩大。先收紧身份和边界，再拆文件，收益比继续堆工具高。

第三个问题是“AI 味”并没有全部从公共表面消失。本轮已整理 README、安装/设计/审计文档和新版本记录，但旧提交、旧 tag、旧 release 标题和部分源代码注释仍保留历史叙事。它们没有被强行改写，以免破坏公共 Git 历史；如果要改历史，需要单独决定是否接受 force-push。

## 本轮已经收掉的缺陷

| 项目 | 证据 | 状态 |
| --- | --- | --- |
| 状态文件包含 Cookie，却按 `0644` 写出 | 本机原 `~/.dsh/storages/lingxu-ctf/state.json` 可被同机其他用户读取 | `fixed`：目录 `0700`、文件 `0600`，并有 POSIX 回归用例 |
| DSH 当前团队投递事件在 `data.content`，旧解析器只看嵌套字段 | DSH 会话日志中的 `user/message` + `source.kind=team-message` | `fixed`：兼容当前和旧两种结构 |
| 慢的旧会话请求会覆盖新会话的 token 缓存 | 客户端 `usageCache` 原来只有一个 key，没有请求代次 | `fixed`：请求 generation + 回归用例 |
| 同一 `messageId` 在不同赛事间被误判为重复 | 消息 ID 不是全局赛事身份 | `fixed`：去重键包含 `connKey` |
| 成功但为空的团队被前端当成失败 | `/team` 可合法返回 `ok:true` 且没有成员 | `fixed`：`normalizeTeam` 保留成功状态 |
| 平台解析失败时读取全部队内消息 | `listTeamMessages(undefined)` 会取消赛事过滤 | `fixed`：优先活动连接，无连接时只读 `unknown` |
| provider 返回 `NaN`/`Infinity` 会污染用量合计 | `usageBuckets()` 原来直接 `Math.max(0, Number(...))` | `fixed`：非有限数按 0 处理 |

## 仍应优先处理的缺陷

### B1：会话身份是单槽位（P1，建议下一轮第一项）

`lib/index.js` 的 `deps.session.caller` 是插件级变量。两个会话交替调用 `ctf_*` 工具时，后一次调用会覆盖前一次的 Lead 身份，`GET /lingxu-ctf/team` 可能读取到另一会话的任务板，或因 caller 失效而返回空态。

建议引入不可变的 `SessionContext`：

```text
{ sessionId, caller, connKey, eventId, capturedAt }
```

工具执行时按 `sessionId` 写入 Map，HTTP 路由从显式 session 参数或宿主请求上下文取同一个 ID；没有 ID 时才走“最近会话”兼容路径，并在响应中标记 `inferred`。验收条件：两个并行会话各自创建任务和发消息，交错请求 `/team`、`/usage`、`/state` 仍只看到自己的数据；会话销毁后 Map 能回收。

### B2：团队事件订阅的生命周期没有被显式记录（P1）

`agentTeams` 服务重新装配或热重载时，当前代码可能再次订阅 `session/event`。如果宿主的 `on()` 没有自动随子 fiber 清理，就会重复落盘。下一轮应保存 disposer、订阅代号和最后处理的事件序号，并在服务替换时先取消旧订阅。验收条件：服务启动/停止/重启各两次，同一投递只落一条记录。

### B3：用量折叠只保留最后一个 step（P1）

`foldTokenUsage()` 和增量 `mergeUsageFold()` 以一个 `last` 槽判断替换。如果日志中两个 step 交错写入，后一个 step 会让前一个 step 失去替换关系，累计值可能重复或少算。建议把槽位改成 `Map<turn,step,retry>`，并用真实 DSH 投影 fixture 做逐桶对照；没有 turn/step 的事件要单独计入“无法对账”，不能静默并入同一个槽。

### B4：显式 session ID 不存在时自动读“最近日志”（P1，工具侧已优先捕获 session ID）

当前工具执行会优先记录 `exec.sessionId`，再退回 agent id；老宿主仍可能只有 agent id，于是会走最近日志兼容路径。这在多会话环境里仍可能显示另一会话的数字。建议 UI 正常路径要求明确 `sessionId`；只有诊断命令允许 fallback，并把 `inferred` 提升到醒目的状态，而不是只放在小字里。验收条件：传入不存在的 ID 时普通面板不展示别的会话数值。

### B5：附件下载没有统一的大小和落盘预算（P1）

`downloadAttachment()` 使用 `response.arrayBuffer()`，大附件或异常响应会同时占用内存和磁盘。建议设置可配置上限（默认 64 MiB）、流式写临时文件、写完后原子改名，超限主动 abort；同时校验 `Content-Length`、实际字节数和目标路径。验收条件：超限返回可读错误，原目录不留下半文件。

### B6：配置写接口需要明确的字段白名单（P1，字段校验已先收紧）

当前版本已经拒绝未知键和错误类型，空值仍按“不修改”处理。剩下的是边界：Cookie 等 secret 仍可由本机配置卡片写入，因此需要确认这条本地路由是否有 DSH 自带的同源保护；若没有，应增加本地请求校验或明确只允许宿主内部调用。

### B7：诊断响应不应默认暴露绝对路径（P2）

`/reports` 当前为本地 UI 提供 `absPath`，`/diag` 还会返回工作目录、方法和限流统计。它们在本机开发很方便，但一旦 web server 被代理或共享端口，就会泄露用户目录结构。建议普通响应只给相对路径和稳定 ID，绝对路径只在显式诊断开关下返回。

### B8：赛段探测失败时可能继续沿用上一赛事工具（P2）

`createStageToolRegistry.sync()` 为了避免网络抖动清空工具，会保留旧 AWD/CFS 注册。切换赛事后若探测失败，用户可能调用到上一场赛事的工具。建议把状态拆成 `known / unknown / none / present`；`unknown` 时工具可以保留名称，但执行前必须再次确认当前连接和赛段归属。

### B9：多进程写 store 仍可能互相覆盖（P2）

`CtfStore` 只有进程内 `_writeChain`，临时文件名固定为 `state.json.tmp`。两个 DSH 进程共享同一 `DSH_HOME` 时，后写者可能覆盖前写者。下一轮需要宿主 storage service、文件锁，或唯一临时文件加 rename/锁协议，并做双进程压力用例。

### B10：限流器是进程级（P2）

多个插件进程或多个 DSH 实例各自维护一套 host limiter，平台看到的总速率仍可能超限。若产品明确只支持单实例，应在文档和启动检查中写清；若要支持多实例，需要把配额协调放到宿主服务。

### B11：客户端轮询还缺少请求代次（P2）

服务端已有 TTL 和 single-flight，但视图和浮动面板的独立请求仍可能在切换赛事后晚到，并覆盖新状态。客户端应为 `/state`、`/team`、`/reports` 使用 `AbortController` 或 request generation；响应的 `connection.key` 不匹配当前选择时直接丢弃。

### B12：平台接口没有能力版本表（P2）

凌虚、AWD、CFS 和理论题的字段目前散在适配器与工具描述中。平台改字段时，失败常表现为“空列表”，不容易定位。建议建立 `capabilities` 响应和 fixture 目录，记录每个 endpoint 的请求、成功、未配置和版本差异；live 检查只验证当前账号允许的最小只读路径。

## 建议的研发顺序

1. **身份与隔离**：完成 `SessionContext`、事件订阅清理、赛事 key 贯穿路由和日志。
2. **存储与安全**：附件预算、配置白名单、诊断脱敏、多进程写入策略。
3. **用量对账**：Map 槽位、重试边界、明确 session fallback，和 DSH 投影做 fixture 对照。
4. **平台契约**：能力探测、错误分类、版本化 fixture，再处理 AWD/CFS 的细节扩展。
5. **客户端拆分**：在契约稳定后，把 `lib/client.js` 拆成数据模型、路由请求、渲染片段、宿主装配四层；保持最终 classic bundle 接口不变。
6. **真实环境验收**：DSH 桌面端、有效凌虚账号、Windows 安装、两个并行会话、长日志和热重载各跑一次。

不要先做“全平台抽象”、自动夺取环境、复杂队列或重写所有历史提交。这些事情会扩大变量，却不能先解决身份和数据归属问题。

## 接下来每个版本的放行门槛

| 门槛 | 必须看到的证据 |
| --- | --- |
| 静态回归 | `npm test` 全通过；`node --check`；`git diff --check` |
| 契约回归 | 当前 DSH 事件 fixture、sessions/projection fixture、平台错误 fixture |
| 安全回归 | state mode、未知配置键、附件超限、绝对路径脱敏 |
| 并发回归 | 两个 session、两个赛事、至少一个热重载/服务重连场景 |
| live 回归 | 有效 Cookie 下 smoke/e2e；没有凭据时明确记 `unverified` |
| 交付回归 | DSH 桌面 UI 视觉验收、Windows 安装结果、发布说明只写用户可感知变化 |

## “去 AI 味”的具体规则

后续代码和文档按以下规则收敛：

- 注释只解释不明显的约束、输入输出和失败边界；“真实事故”“第几项问题”“已证伪坑”放进审计记录，不放在每个函数上方。
- 一个模块头只保留职责和公共入口，契约表放 `docs/DSH-API-NOTES.md`。
- prompt 和错误文本用用户要做的动作说话，少用“完整、深度、闭环、如实、硬要求”等自我评价词。
- commit 标题写功能变化，例如“修正多会话团队消息归属”，正文列出可验证影响；不要把“全面升级、深度适配、18 项集中修复”当标题。
- release note 只写本版本实际改变的行为，并单列“未验证的 live 项”。

本轮先做了不改变公共历史的前向整理。旧 commit/tag/release 的标题和正文仍然存在；是否在新分支上重写并 force-push，等确认仓库协作方式后再做。
